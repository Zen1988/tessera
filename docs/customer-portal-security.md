## Implemented first correction

CustomerTicketZTSMAction previously had no explicit RequestMethod/ChallengeToken check despite handling ticket state, Dynamic Field and evidence writes. Native InterfaceCustomer does not provide a global equivalent to InterfaceAgent's token gate. Existing ordinary CustomerTicketMessage and CustomerTicketProcess explicitly call ChallengeTokenCheck(Type=>Customer).

Added an admission check after ticket read permission/type resolution and before all runtime-action mutation branches. Mutating requests require POST, nonempty request/current session tokens with equality, then native customer ChallengeTokenCheck. Equality keeps this endpoint protected even if framework SessionCSRFProtection is disabled; tokens from a different customer session are deliberately not accepted. Missing/forged proof is refused. No CSRF tokens appear in logs. Successful action entitlement/lifecycle validation still runs normally; the token does not grant ticket access.

Four terminal JSON subactions retain read access because Run returns before action mutations. Assessment/Assess and Diagnosis/Diagnose workspace/inline exceptions are matched to ticket type plus action plus subaction. Inline or Submit parameters cannot exempt a different mutating action. Unknown routes default to mutation checks.

Native Template::Provider inserts ChallengeToken into form templates; existing runtime and diagnosis forms are POST. Live form/token persistence still needs browser acceptance after a future deployment. No mass changes or weakening of action/record permissions. No schema, governance or ticket data modifications.

## Rendering work still pending

CustomerTicketZoom.tt contains two ExecuteScripts helpers. Fetched assessment/diagnosis HTML is inserted using innerHTML, then every script in that fragment is recreated as executable. This is a security-sensitive sink and strict-CSP obstacle, not proof that attacker-controlled data currently reaches it unescaped. Do not simply remove it and break form initialization. Trace generated workspace HTML and each data context, move trusted initialization into registered external JS, use explicit initializer entry points and stop executing arbitrary fragment scripts. Test malicious field/catalog labels, remarks, risk details and stored article content in the real rendering path. Preserve rich-text sanitization and sandbox CSP for articles/attachments.

Next audit surfaces: ticket create/follow-up, CustomerTicketZoom/actions, assessment/diagnosis/treatment workspaces, ActivityDialog, customer ConfigItem/risk lookup APIs, uploads/downloads/exports and public/login/recovery. Review permission scope, method/CSRF, ID references, context-specific output encoding, URLs and supported rich HTML. Backend validation and client presentation are separate controls. No blanket customer-portal-safe claim is made.

## Extensionless customer URLs

Yes, expose a customer address such as `/portal` using a server route/reverse proxy while keeping Perl/PSGI behind it. HTML/XHTML describe response documents, not replacement server runtimes. A Python proxy adds another application boundary and is unnecessary just to hide `.pl`. Suffix hiding is presentation and compatibility work, not an injection control.

Source evidence: native otobo.psgi mounts `/customer.pl` to InterfaceCustomer; Layout derives CGIHandle/Baselink from Request::ScriptName. A route change must preserve the external ScriptName/Baselink, query/action parameters, POST bodies, cookies/session scope, redirects, AJAX URLs, static paths and email/deep links. Changing only a proxy alias risks leaking/breaking old URLs. No production route/configuration or exact new public URL was chosen or changed here. Keep legacy URL compatibility during migration; never redirect mutation POST to a GET.

References: https://httpd.apache.org/docs/2.4/mod/mod_proxy.html and https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html.
