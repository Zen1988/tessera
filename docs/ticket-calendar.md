# Ticket Calendar (TESSERA-Base 0.0.169)

The agent and customer Tickets calendars are a read-only projection of tickets, not a separate appointment ledger. Every refresh searches with the authenticated agent and `Permission => ro`, then rechecks `TicketPermission(Type => ro)` before loading or returning a title, number, time or link. A direct Events URL has the same checks. OTOBO ticket group/queue permissions remain the authority; no team list or calendar membership creates a new grant.

- Change uses exported `ZTicket-ScheduleStart` and `ZTicket-ScheduleFinish`.
- Incident uses OTOBO's native ticket `Created` timestamp as its start, even when `ZTicket-ActualStart` exists. `TicketCreate` writes `create_time` with `current_timestamp` for both manual and automated creation paths.
- ServiceRequest uses exported `ZTicket-ActualStart`, falling back to ticket creation when it is empty. Incident and ServiceRequest use `ZTicket-ActualFinish` for the end; for a closed ticket without actual finish, the latest closed-state history transition supplies the end. An open ticket runs through the current time.
- The browser renders Unix instants in its local timezone. Tickets outside the requested 1–62 day window are excluded. Search is capped at 20,000 candidates per branch and rejects overflow instead of silently showing an incomplete calendar.
- Month, week and day views link to AgentTicketZoom or CustomerTicketZoom for the respective viewer. Tickets update the next time the view refreshes; no duplicate appointment or synchronization job is created.

Installation registers `AgentTESSERATicketCalendar` for agents and adds Calendar beside Dashboard and List in the customer portal's Tickets view. The customer Events endpoint starts from the same filtered IDs as CustomerTicketOverview, including SupportAssignment visibility, then rechecks `TicketCustomerPermission(ro)` or the same `ZTSMUserIDCheck(ro)` fallback as CustomerTicketZoom before loading any ticket data. The client cannot submit arbitrary ticket IDs. Change is blue, Incident orange and ServiceRequest green, with a visible legend. OTOBO's appointment calendar remains separately available. Both views are read-only. Live installation and UI/permission acceptance remain pending.

The 0.0.164 package includes the native FullCalendar stylesheet in the customer skin. Earlier 0.0.163 customer screenshots show unstyled calendar controls because OTOBO shipped that stylesheet only for the agent skin. Customer portal button overrides are scoped to the calendar toolbar.

In 0.0.165 the customer calendar groups every visible Change, Incident, or ServiceRequest child with `ZTicket-Parent` under its master number. A master lacking customer read permission is a number-only group heading, without a title, link, or hidden siblings. A readable master has its title and zoom link. The IPC customer scope no longer fails merely because it exceeds 20,000 authorized tickets. Event-processing exceptions are recorded in the system log while the browser receives a generic error.

In 0.0.166 ticket titles use the ASCII `>` separator. Customer grouped ticket entries show the configured standard front-page category badges (Priority, Type, Queue, Service, State and Owner), reading `Ticket::Frontend::CustomerTicketCategories` and its exact per-value ColorSelection / ColorDefault and ordering. Colors are validated as three- or six-digit hex and badge text is inserted as text, with readable foreground and wrapping. The existing calendar bar/legend type palette is retained. No SysConfig defaults or ticket data are rewritten. Dynamic-field category badges are not added by this change.

In 0.0.167 the grouped panel uses the selected month/week/day interval, excluding tickets occurring only in adjacent-month grid days. It rebuilds after every event render, including cached navigation, and shows browser-local execution date ranges. A ticket spanning months legitimately appears in each overlapping selected period; the calendar grid retains adjacent days. Stored ticket dates are unchanged.

In 0.0.168 customer event requests compute only the required All scope, retaining its standard/SupportAssignment union and per-ticket read rechecks. A failed request retries once automatically; after two failures the error stays visible. Superseded requests cannot update the current view error state or start a retry. This improves recovery but does not establish the cause of the reported deployed first-load failure.

In 0.0.169 both calendars register initialization at native Core.Init APP_MODULE, after configuration insertion/CONFIG_LOADED. Earlier scripts registered jQuery ready during ModuleJS loading, before the footer config-ready callback; their initial fetch could build an invalid URL from unavailable Baselink. Month navigation occurs later and succeeds. Initial and navigated ranges both come from FullCalendar; no synthetic month navigation is used.
