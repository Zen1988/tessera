TESSERA ControlObjective policy examples
=========================================

The object and field names below are authored names. Internal database IDs must
never be placed in a policy. A missing field, failed conversion, or unsupported
expression evaluates to UNKNOWN and never silently satisfies a control.

ZRM-PolicyFilter
----------------

# This control applies only to active Change tickets.
APPLIES WHEN
    @TICKET.Type EQUALS "Change"
AND @TICKET.StateType DOES NOT EQUAL "closed"

ZRM-PolicyEvaluation
--------------------

# Actual execution must have started within the last calendar month interval.
REQUIRE
    @TICKET.ZTicket-ActualStart IS NOT EMPTY
AND DATETIME(@TICKET.ZTicket-ActualStart) IS ON OR AFTER 1 MONTH AGO

Numeric example
---------------

REQUIRE
    PRODUCT OF [NUMBER(@TICKET.ZRM-LikelihoodFactor), NUMBER(@TICKET.ZRM-ImpactFactor)] IS AT MOST 9

Initial executable grammar
--------------------------

- Roots: @TICKET and @CONTROLOBJECTIVE.
- Fields: native fields or exact Dynamic Field names.
- Logic: AND and OR at the start of a condition line.
- Comparison: EQUALS, DOES NOT EQUAL, IS EMPTY, IS NOT EMPTY,
  IS GREATER THAN, IS LESS THAN, IS AT LEAST, IS AT MOST,
  IS ON OR AFTER, IS ON OR BEFORE, CONTAINS, STARTS WITH, ENDS WITH.
- Conversion: NUMBER(...), STRING(...), DATE(...), DATETIME(...).
- Arithmetic: multiplication, division, and PRODUCT OF [...].
- Time: NOW and N DAYS/WEEKS/MONTHS/YEARS AGO.

Recursive GovernanceObject, ITSMConfigItem, and MELT traversal, named object
selection, collections, schedules, business calendars, and LET variables remain
reserved grammar. Until implemented, using them returns UNKNOWN.

Manual control attestation
--------------------------

The Service is not declared in policy text. The existing Service Request
workflow is selected through the ControlObjective's ZRM-Service field and owns
ticket creation, routing, assignment, and lifecycle.

NEW @TICKET
SET @TICKET.Title = "Annual input-validation attestation"
SET @TICKET.Queue = "Governance"
SET @TICKET.CustomerUser = "customer.login"
SET @TICKET.Attestation = [
  { ZRM-Query = "Confirm server-side validation is applied to every untrusted input.", ZRM-Response = "" },
  { ZRM-Query = "Confirm invalid input is rejected and recorded.", ZRM-Response = "" }
]
SUBMIT

EXPECT:
@TICKET.Attestation[0].ZRM-Response EQUALS "Yes"
AND @TICKET.Attestation[1].ZRM-Response EQUALS "Yes"
THEN PASS
ELSE FAIL

The equivalent indexed authoring form is:

LET @TICKET.Attestation[0].ZRM-Query = "Confirm server-side validation is applied."
LET @TICKET.Attestation[0].ZRM-Response = ""

NEW @TICKET creates a service-backed draft. SET/LET assignments populate it.
SUBMIT hands it to the existing Service Request workflow. No queue, requester,
owner, or process routing is hardcoded by the control policy.

EXPECT is evaluated by the service workflow's ZRMControlEvaluate transition
action at the workflow's configured completion point. The action receives the exact
ConfigItem Control ID being executed; ZRM-TKInstance remains a control target,
not a pointer to an attestation ticket.
UNKNOWN never becomes Pass. The linked ConfigItem Control receives ZRM-Result
and ZRM-LastRun; the reusable ControlObjective does not store runtime history.

FAIL records the result only. It does not implicitly create remediation work.
A separate authored conditional action such as `IF FAIL THEN ...` is required
before a future action executor may submit a follow-up ticket.
